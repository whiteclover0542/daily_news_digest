# 뉴스 요약 앱 — 성능 평가 계획서

> 발표는 없지만, 이 평가서 자체를 포트폴리오 산출물로 삼는다.
> 파이프라인 구현 완료 후 `## 7. 평가 결과 기록` 표를 채워 넣는다.

---

## 1. 평가 목적

- LLM 파이프라인(요약·카테고리 분류)의 품질을 **정성 + 정량**으로 검증하고 문서화한다.
- "그냥 잘 되는 것 같다"가 아니라, 재현 가능한 절차와 지표로 근거를 남긴다.
- 프롬프트/모델 버전을 바꿀 때 회귀(regression) 여부를 같은 기준으로 비교할 수 있게 한다.

## 3. 평가 지표

### 3-1. 요약 품질 — G-Eval (LLM-as-a-Judge)

[G-Eval (Liu et al., 2023)](https://arxiv.org/abs/2303.16634) 방식 채택: LLM에게 **평가 기준 + 평가 단계(CoT)**를 프롬프트로 주고 1~5점을 채점하게 한다. 원 논문의 요약 평가 축(Coherence/Consistency/Fluency/Relevance)을 뉴스 요약에 맞게 재정의한다.

| 축 | 정의 | 1점 (나쁨) | 5점 (좋음) |
|---|---|---|---|
| **Relevance** (관련성) | 원문의 핵심만 담고 불필요한 디테일은 뺐는가 | 지엽적인 내용 위주로 요약 | 핵심 사실만 압축 |
| **Consistency** (사실 일관성) | 원문에 없는 내용을 지어내지 않았는가 (hallucination 여부) | 원문에 없는 수치/인물/사건 포함 | 원문 사실과 완전히 일치 |
| **Fluency** (유창성) | 문장이 자연스럽고 읽기 쉬운가 | 비문/어색한 번역투 | 매끄러운 한국어 문장 |
| **Coherence** (응집성) | 요약문 전체가 논리적 순서로 잘 짜여 있는가 | 문장들이 따로 노는 느낌 | 하나의 글로 잘 읽힘 |

> 요약 앱 특성상 **Consistency(사실 일관성)** 가 가장 중요하다. 뉴스 요약에서 hallucination은 치명적 결함으로 간주하고 별도 가중치를 둔다.

**목표치 체크**

| 축 | 목표치 | 실측값 | 달성 여부 |
|---|---|---|---|
| Relevance | ≥ 4.0 / 5.0 | - | ⬜ |
| Consistency | ≥ 4.5 / 5.0 | - | ⬜ |
| Fluency | ≥ 4.0 / 5.0 | - | ⬜ |
| Coherence | ≥ 4.0 / 5.0 | - | ⬜ |

**채점 방식**
- 기사 1건당 4개 축 각각 1~5점, judge 모델에게 동일 기사를 N=3회 채점시켜 평균값 사용 (변동성 완화)
- judge 모델은 요약을 생성한 모델과 **다른 모델**(또는 최소 다른 호출)을 쓰는 것을 권장 — self-evaluation bias 방지

**프롬프트 템플릿 예시 (Consistency 축)**

```
당신은 뉴스 요약의 품질을 평가하는 전문 평가자입니다.

[평가 기준] Consistency (사실 일관성): 요약문이 원문 기사의 사실과 일치하는지,
원문에 없는 내용을 지어내지 않았는지를 평가합니다.

[평가 절차]
1. 원문 기사를 읽고 핵심 사실(인물, 수치, 사건, 인과관계)을 정리한다.
2. 요약문을 읽고 각 문장이 1번에서 정리한 사실과 부합하는지 확인한다.
3. 원문에서 확인할 수 없는 내용, 왜곡된 내용이 있으면 감점한다.
4. 1~5점 중 하나로 점수를 매기고, 근거를 한 문장으로 남긴다.

[원문 기사]
{article}

[요약문]
{summary}

[출력 형식 (JSON)]
{"score": <1-5>, "reason": "<한 문장 근거>"}
```

Relevance/Fluency/Coherence도 같은 골격(기준 설명 → 단계별 절차 → 점수+근거)으로 축만 바꿔 작성한다. `backend/ai/prompts/` 아래 `eval/` 서브폴더를 만들어 4개 템플릿을 관리하는 것을 권장.

### 3-2. 사실 일관성 보강 체크 (선택)

G-Eval의 Consistency 점수만으로는 hallucination을 놓칠 수 있어, 저비용 보강 체크를 함께 둔다.

- **문장 단위 검증**: 요약문을 문장 단위로 쪼개, 각 문장이 원문 어느 부분에서 근거하는지 LLM에게 답하게 하고 근거를 못 찾으면 flag
- 자동화 난이도가 높으면 MVP 단계에서는 생략하고, 확장 단계에서 추가

**목표치 체크**

| 항목 | 목표치 | 실측값 | 달성 여부 |
|---|---|---|---|
| 적용 여부 (MVP 이후 도입) | - | - | ⬜ |

### 3-3. 자동 지표 (참고용, LLM judge 보완)

| 지표 | 설명 | 비고 |
|---|---|---|
| ROUGE-1/2/L | 원문-요약 간 어휘 중복도 | 추상 요약엔 한계 있음, 참고용 |
| 요약 길이 준수율 | 목표 글자수(예: 200자 이내) 준수 비율 | 규칙 기반, 계산 쉬움 |
| 응답 성공률 | LLM 호출 성공 / 전체 호출 | 파싱 실패, timeout 등 포함 |

G-Eval이 사람 평가와 상관관계가 가장 높다고 알려져 있으므로 **주 지표는 G-Eval, ROUGE는 보조 지표**로 취급한다.

**목표치 체크**

| 지표 | 목표치 | 실측값 | 달성 여부 |
|---|---|---|---|
| ROUGE-L | ≥ 0.30 | - | ⬜ |
| 요약 길이 준수율 | ≥ 95% | - | ⬜ |
| 응답 성공률 | ≥ 98% | - | ⬜ |

### 3-4. 카테고리 분류 평가

- **Accuracy**: 전체 정답률
- **Macro F1**: 카테고리별 불균형(예: 정치/경제 기사가 스포츠보다 많음)을 고려한 지표
- **Confusion Matrix**: 어떤 카테고리끼리 혼동이 잦은지 파악 (예: 경제 ↔ IT)

**목표치 체크**

| 지표 | 목표치 | 실측값 | 달성 여부 |
|---|---|---|---|
| Accuracy | ≥ 85% | - | ⬜ |
| Macro F1 | ≥ 0.80 | - | ⬜ |
| Confusion Matrix | 정성 검토 (수치 목표 없음) | - | ⬜ |

### 3-5. 파이프라인/시스템 지표

| 지표 | 설명 |
|---|---|
| 수집 성공률 | 수집 시도 대비 정상 수집된 기사 비율 |
| 중복 제거율 | 전처리 단계에서 걸러진 중복 기사 비율 |
| 파이프라인 실행 시간 | 새벽 배치 전체 소요 시간 |
| LLM API 실패율/재시도율 | rate limit, timeout 등으로 인한 재시도 빈도 |
| 토큰 사용량/비용 | 기사당 평균 토큰 수 × 단가 |

**목표치 체크**

| 지표 | 목표치 | 실측값 | 달성 여부 |
|---|---|---|---|
| 수집 성공률 | ≥ 95% | - | ⬜ |
| 중복 제거율(잔존) | ≤ 5% | - | ⬜ |
| 파이프라인 실행 시간 | ≤ 30분 | - | ⬜ |
| LLM API 실패율/재시도율 | ≤ 2% | - | ⬜ |
| 토큰 사용량/비용 | 실측 후 확정 | - | ⬜ |

### 3-6. 지표 요약표 (목표치)

MVP 기준으로 잡은 1차 목표치. 실제 golden set으로 1차 평가를 해본 뒤 비현실적이면 조정한다. 실측값과 함께 보는 전체 표는 [7-1. 지표별 목표치 vs 실측값](#7-1-지표별-목표치-vs-실측값)에 기록한다.

| 구분 | 지표 | 목표치 | 측정 방법 | 우선순위 |
|---|---|---|---|---|
| 요약 품질 | G-Eval Relevance | ≥ 4.0 / 5.0 | LLM judge, N=3 평균 | 중 |
| 요약 품질 | G-Eval Consistency | ≥ 4.5 / 5.0 | LLM judge, N=3 평균 | **최우선** |
| 요약 품질 | G-Eval Fluency | ≥ 4.0 / 5.0 | LLM judge, N=3 평균 | 중 |
| 요약 품질 | G-Eval Coherence | ≥ 4.0 / 5.0 | LLM judge, N=3 평균 | 중 |
| 요약 품질(보조) | ROUGE-L | ≥ 0.30 | 원문-요약 lexical overlap | 낮음 (참고용) |
| 요약 품질(보조) | 요약 길이 준수율 | ≥ 95% | 규칙 기반 (글자수 제한) | 중 |
| 요약 품질(보조) | LLM 응답 성공률 | ≥ 98% | 파싱/timeout 실패 제외 비율 | 높음 |
| 분류 | Accuracy | ≥ 85% | golden set 대비 정답률 | 높음 |
| 분류 | Macro F1 | ≥ 0.80 | golden set 대비 | 높음 |
| 파이프라인 | 수집 성공률 | ≥ 95% | 수집 시도 대비 정상 수집 | 높음 |
| 파이프라인 | 중복 제거율 | 잔존 중복 ≤ 5% | 전처리 후 샘플 검수 | 중 |
| 파이프라인 | 배치 실행 시간 | ≤ 30분 | 새벽 배치 전체 소요 시간 | 중 |
| 파이프라인 | LLM API 실패율/재시도율 | ≤ 2% | 호출 로그 집계 | 중 |
| 파이프라인 | 기사당 평균 토큰 비용 | 실측 후 확정 | 토큰 수 × 단가 | 낮음 |

> Consistency는 hallucination과 직결되므로 다른 축보다 목표치를 높게(4.5) 잡고 최우선 순위로 둔다. 목표 미달 시 프롬프트 수정을 최우선으로 대응한다.

## 4. 평가 데이터셋 (Golden Set)

- 카테고리별 20~30개씩 샘플링 → 총 100~150개 기사
- hoya·whiteclover가 절반씩 나눠 사람이 직접 요약/카테고리를 라벨링(정답셋 작성)한 뒤 서로 교차 검토(cross-check)
- 프롬프트·모델 버전이 바뀔 때마다 같은 golden set으로 재평가해 회귀 여부 비교

---

## 5. 평가 절차

1. 파이프라인을 golden set 기사에 대해 실행해 요약/카테고리 예측 결과 수집
2. G-Eval judge 프롬프트로 요약 채점 (기사당 N=3회 반복 → 평균)
3. ROUGE 등 자동 지표 계산
4. 카테고리 예측 결과로 Accuracy/F1/Confusion Matrix 계산
5. 결과를 `## 7. 평가 결과 기록` 표에 정리, 특이 사례(hallucination 등)는 별도로 캡처해 남김

---

## 6. 사람 평가와의 스팟 체크 (선택)

- golden set 중 10~20개를 무작위로 뽑아 사람이 직접 1~5점을 매기고 G-Eval 점수와 상관관계를 확인
- G-Eval judge가 신뢰할 만한지 최소 1회는 검증해두면 평가서의 설득력이 올라감

## 8. 향후 확장

- 프롬프트 버전 A/B 비교 (예: few-shot 유무, 길이 제한 방식 변경)
- 실사용 피드백(좋아요/신고 등)이 생기면 G-Eval 점수와 실사용 반응 비교
